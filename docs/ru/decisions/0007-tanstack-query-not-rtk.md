# 0007. TanStack Query, а не Redux Toolkit / RTK Query

**Статус:** принято · ноябрь 2026

## Контекст

К v0.4 в экранах накопились мутации, шторки и тосты, и экраны стали толстыми. Первая
мысль — то, что я знаю по работе: Redux Toolkit и RTK Query, один стор на всё.

## Что на самом деле нужно хранить

- **Данные с сервера** — разделы, продукты, покупки, участники. Это кэш запросов
  с оптимистичными правками и перечитыванием по Realtime. Это уже делает TanStack Query.
- **Открытая шторка** и **текущий тост** — две крошечные переменные, которые надо уметь
  менять из любого места (обработчик, мутация, код вне компонентов).
- Всё остальное (тема, язык, свёрнутые разделы) — по сути настройки в `localStorage`.

## Варианты

- **RTK + RTK Query.** Знакомо, хорошие devtools. Но поверх уже работающего кэша — второй
  кэш с той же задачей, переписывание оптимистичных правок на `onQueryStarted` и слой
  слайсов ради двух переменных. Плюс килобайты в бандле, а он грузится целиком
  ([0004](0004-safe-updates.md)).
- **Zustand / Jotai.** Легче, но тоже новая зависимость ради двух значений.
- **Остаться на TanStack Query и сделать маленький стор руками.** `createStore` на
  `useSyncExternalStore` — 30 строк.

## Решение

- Серверные данные — TanStack Query. Мутации уходят из экранов в `data/hooks`:
  `useCreateProduct`, `useSetProductState`… Экран только вызывает `mutate`.
- Разовые действия без оптимизма (приглашения, участники, аккаунт) — `useAction`:
  тосты успеха и ошибки и что перечитать описаны в одном месте.
- Тост — обычная функция `notify(key, params)`, а не хук: вызывается откуда угодно.
- Открытая шторка — тот же маленький стор (следующий шаг).

## Последствия

- Нет Redux devtools; для кэша есть devtools TanStack Query, если понадобится.
- Если состояние клиента когда-нибудь станет сложным, к Redux можно вернуться — но не
  раньше.
