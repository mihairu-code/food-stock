# 0002. Supabase как бэкенд

**Статус:** принято · ноябрь 2026

## Контекст

Нужны: хранение, вход, разделение данных по домам и живая синхронизация между
участниками. Сервер писать не хочется — хочется быстрее дойти до рабочего MVP.

## Варианты

- **Свой API на Go + Postgres.** Я как раз потихоньку учу Go, было бы полезно. Но это
  авторизация, CRUD, вебсокеты и деплой сервера — неделя-две только на то, что
  Supabase даёт из коробки.
- **Firebase.** Быстро, но документная модель: связи «дом → разделы → продукты»
  и каскадное удаление пришлось бы держать руками в клиенте.
- **Supabase.** Обычный Postgres, вход, Realtime, доступ по строкам (RLS). Клиент
  ходит в базу напрямую, правила доступа — в SQL.

## Решение

Supabase: Postgres + Auth + Realtime. Каждая таблица с данными привязана
к `household_id` и закрыта политикой RLS «вижу только дома, где я участник».
Действия, которые должны пройти целиком (принять приглашение, купить ручную позицию),
— функции в базе (RPC).

В клиенте — один интерфейс хранилища `Backend` и две реализации: Supabase
и локальное демо в `localStorage`. Демо нужно, чтобы делать интерфейс, не трогая базу,
и чтобы проект запускался у кого угодно без ключей.

## Последствия

- Безопасность держится на RLS. Значит, политики надо тестировать — настоящим
  Postgres, а не моками.
- Ключ `service_role` в клиент не попадает никогда.
- Go откладываю. Если когда-то понадобится своя логика на сервере — Edge Functions
  или отдельный сервис рядом.
